Testing Winter Boot Applications with PHPUnit

Winter Boot does not ship its own test runner. Use PHPUnit, the standard PHP test framework (the PHP counterpart of JUnit). This page shows two kinds of tests:

  • Unit tests — create a class with new, pass in stubs for its dependencies, and test it in isolation. Fast, and no framework involved.
  • Integration tests — boot the real application context once, using the test profile, and test beans exactly as the application wires them, without starting the HTTP server.

Note

Tests assume Swoole is installed and enabled, like the application itself.

Setup

Section titled “Setup”

  1. Install PHPUnit

    Register your test namespace for autoloading in composer.json, next to your application namespace, then run composer dump-autoload:

  2. Add a test starter with the test profile

    The test starter points at the same config directory as the real application, but sets profile: 'test'. The framework’s property context then loads config/application-test.yml instead of config/application.yml, and the logger loads config/logger-test.yml (falling back to config/logger.yml when there is no profile-specific file). The profile file must contain the complete configuration — it is not merged with application.yml.

    WinterWebApplication is the plain web runner: under PHPUnit (CLI) it builds the full context — configuration, beans, modules, #[OnApplicationReady] — and returns without serving HTTP, so no server ever starts.

    Note

    When a test needs a running server (HTTP-level tests against a live port), boot the same starter with WinterWebSwooleApplication instead — it starts the Swoole HTTP server and blocks, so run it as a separate process your tests call over HTTP.

  3. Add the test configuration

    Give tests their own profile file, so they never touch your real database or services. PDBC datasources use SQLite in-memory here:

    To silence or redirect test logging, add config/logger-test.yml in the same monolog-cascade schema as logger.yml. Without it, the normal logger.yml applies.

  4. Swap real beans for mocks with #[Bean] methods

    A #[Configuration] class can return a mock when the active profile is test and the real bean otherwise. Read the profile flag from the configuration you defined in both YAML files:

    Set myApp.profile to the matching value in each file (prod in application.yml, test in application-test.yml). The same pattern works for any external client — payment gateways, mail senders, third-party SDKs — that must not run for real in tests.

  5. Add a context holder and bootstrap file

    The runner returns void, so a small test-support bean captures the booted context into a static holder. ApplicationContext is injectable in any bean, and eager: true on the test starter guarantees the capture runs during boot:

    Keep the $_SERVER['argv'] handling. Without it, running phpunit --filter ... fails, because Winter Boot reads the command line at startup.

    Keep the disableTimer() call too. Without it, PHPUnit never exits once a test has used a datasource: the idle-check timer keeps Swoole’s event loop running after the last test.

Unit tests

Section titled “Unit tests”

Beans that receive their dependencies through the constructor can be created with new in a test, with PHPUnit stubs standing in for the dependencies. No container is needed:

Tip

Prefer constructor injection for anything you want to unit-test. Dependencies injected into properties with #[Autowired] or #[Value] are private and set by the container, so a class built with new does not have them.

Integration tests

Section titled “Integration tests”

Fetch beans from the booted test context with beanByClass() (or beanByName()). They are the real, fully wired beans, using application-test.yml — mocks where your #[Bean] methods return them:

The context is built once and shared by every test in the run, just as beans are shared in the real application. Tests that change shared state (a database row, a cache entry) should clean it up, or rely on the fresh in-memory SQLite database each run starts with.

What runs in tests, and what does not

Section titled “What runs in tests, and what does not”

The test bootstrap builds the full context but does not start the server. Everything that lives inside beans works — dependency injection, #[Value], #[PostConstruct], #[OnApplicationReady], datasources and PdbcTemplate, #[Transactional], #[Cacheable] and other AOP attributes, and RestTemplate.

The parts that need the running server are not started:

Feature In tests
HTTP routing, controllers via HTTP, interceptors Not served. Test controller methods by calling them directly, and test the logic in services.
#[Async] Calling an #[Async] method on a bean from the context throws BeansException (no async worker pool). Put the work in a plain method or service and test that.
#[Scheduled], #[DaemonThread] Not started. Call the method directly to test its logic.
Local KV and queue stores Not started.

Note

The #[WinterBootTest] attribute marks a class as a bean, like #[Service]. It is useful for test-only helper beans (fixtures, fakes) placed in the tests namespace that your test starter scans. PHPUnit creates test-case classes itself, so #[Autowired] properties on a TestCase are not injected — fetch beans from the context as shown above.
